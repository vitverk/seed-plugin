# Plots and building

Observed in SEED staging, October 2026. Verify current access and boundaries.

- Group membership and plot ownership are distinct: transferring a plot can
  change ownership and management of its equipment, so use the user's actual
  authorization and inspect the resulting owner. Do not control another
  player's Seedling merely because it belongs to the same group.
- Read plot cell bounds and placement responses; map centers alone do not prove
  continuity or a valid location. Check what is owned before moving objects.
  Empty a container before moving it, provide a usable sleeping alternative and
  verify both the new object and the cleared site after the move.
- Clearing vegetation can have multiple stages. In one trial, harvesting a
  landscape tree converted it to an entity with further harvests, then a stump
  that required removal. An empty landscape scan alone did not prove clearance.
  Inspect spawned entities, remaining harvests and loose piles. For landscape
  actions use the exact tile and grid cell returned by the current tools.
- Inspect a blueprint's material requirements, blocking objects and inbox;
  supply and construction are separate steps. Keep materials already committed
  to other projects visible. Cancelling a new construction can lose delivered
  materials according to the game guide; do not cancel casually.
- The building guide describes editing existing buildings in Build Mode and
  adding windows. Daylight does not replace night lighting. Some equipment may
  wear faster outdoors; inspect its current durability display. Separate
  fire-prone machinery from flammable furnishings when planning interiors.

## Plan a new modular building

Protocol source: user-supplied “SEED: building a modular building via
create_modular_building”, based on SEED `develop`, 2026-10-28. Its examples were
not round-tripped through a server. Treat this as a blueprint format reference,
not evidence that a particular design or placement works in the current world.

For an authorized building objective, choose a practical layout from the user's
purpose, accessible plot, skills and available materials. Continue ordinary
planning and construction within that scope without asking for approval at each
step. A request to plan alone does not authorize creating a site or spending
materials. Keep care and the user's other priorities in view.

Use the read-only `prepare_building_plan` helper when available. It compiles a
single ground floor of rectangular Structure rooms into a command request; it
does not contact the game or create a building. Discover its current input
schema before use. The supported design inputs are:

- `position`: world-space anchor `{x, y, z}`, with `y` at the verified terrain
  height. Room and opening coordinates below are building-local metres, not
  world coordinates. Orientation is part of the layout; there is no separate
  command rotation field.
- `palette`: `shack`, `log`, `plank`, `brick`, `plaxin` or `high_tech`. Choose a
  style the player can build. Optional `color` must belong to that style.
- `rooms`: rectangles with unique `id`, `x`, `z`, `width` and `depth`. Origins
  and dimensions use the 2 m grid; dimensions are positive. Avoid overlaps and
  connect every room to an entrance through doors. Optional room fields
  `floor_style_id`, `palette_name` and `interior_light_id` select known styles;
  omit them for defaults when their current identifiers are not verified.
- `entrances`: at least one opening on an exterior wall. `doors` join rooms on
  shared walls. Both use `x`, `z` and optional `is_small` (default `false`).
  Coordinates identify the start of a wall segment at even grid coordinates:
  west/east wall segments extend toward +z; north/south segments toward +x.
- Optional `windows`: exterior wall segments with `x`, `z` and outward `facing`
  (`north`, `east`, `south`, `west`). The helper uses north = -z and sets window
  height to local y = 1. Use that coordinate convention rather than the source
  example's inconsistent compass labels.

Review the returned bounds, block and opening counts, and unresolved checks.
A successful compile establishes only the helper's local checks. Terrain,
plot access, collision clearance, player skill limits, material costs and game
server validation remain unverified. In particular, inspect the whole footprint
against current buildable plot bounds, allowing the source's 2 m edge margin;
reserve ground-floor space for the inbox and outbox and a usable entrance.
Bare territory and reserved plots are not interchangeable with a buildable plot.
If the tools cannot establish a material placement prerequisite, report that
specific gap rather than inventing a location or calling the plan proven.

The helper emits V2 voxels (2 × 3 × 2 m), required empty arrays and
Brotli-compressed UTF-8 blueprint JSON encoded as base64 `building_data`.
Preserve its generated bytes exactly when submitting. A readable JSON blueprint
or base64 of uncompressed JSON is not a command payload. The source limits
compressed data to 65,536 bytes and also describes a decompressed size limit;
current server rules remain authoritative.

Multiple floors, stairs, elevators, balconies, yards and arbitrary voxel layouts
require separate format and connectivity work; they are not supported by this
helper. Do not silently reduce a requested advanced design to one floor. If the
helper is unavailable, report the missing capability and retain the design;
do not infer that modular building is intrinsically unsupported by SEED.

## Create the site and complete construction

Discover the fresh `PlayerCommand.create_modular_building` schema and the
connected player's identity before writing. Use the existing `send_command`
with the generated request, an authorized `Player` header and that same player
entity as receiver. Do not use system/developer identity or
`Constructible.debug_finish_construction`. Send only one creation at a time.

Inspect the inner command response and returned entity, then read the new site
in the world. Command acceptance creates a construction site, not a usable
finished building. Inspect its actual requirements and inbox; deliver only the
remaining authorized materials, arrange ordinary construction work, and verify
completion and usability before moving residents or equipment into it.

On an explicit validation rejection, fix the identified rule and recheck the
plan and affected world facts before a bounded retry. Do not repeat unchanged
requests or relocate blindly. After a timeout or ambiguous result, inspect the
world for the site before considering another create command; avoid duplicate
sites. Stop when a material prerequisite cannot be resolved within the user's
scope. Record the actual response and verification outcome in dated game notes
so a future session can distinguish a compiled plan, a placed site and a
completed building.
